# ig-agent-watch

Long agent runs fail in three quiet ways: they **drift** (edit files outside the task), **loop** (retry the same failure, or sit idle), and **over-build tests** (grow test infrastructure, weaken assertions). This skill makes the patrol repeatable: a script reports **facts**, the table below turns them into a level, and a human or you decides. The watched agent does not have to cooperate.

`<skill-dir>` is the directory containing this `SKILL.md`. Do not special-case a project, language, build tool or agent.

## Rules

- Read-only. The script never writes in the worktree, fetches, checks out, kills a process or touches the network. Its one write is the `--state` snapshot, and only to a path you pass that is **outside** the worktree.
- The script draws no conclusions. The levels below are defaults; say which threshold you applied.
- Never terminate, signal or message the watched agent. Report first, the human decides.

## Run it

```bash
bash "<skill-dir>/scripts/watch.sh" --worktree <dir> --base <commit> \
  --log <agent.log> [--log ...] --scope 'src/**' --forbid '**/migrations/**' \
  --task-file specs/x/tasks.md --pid-pattern '<regex on the agent command line>' \
  --state <dir-outside-worktree>/watch-state.json
```

| Option | Meaning |
|---|---|
| `--worktree`, `--base` | worktree to inspect and the commit the agent started from (required `--base`). Everything is measured as working tree vs `base`, including untracked files |
| `--log` (repeat) | agent output logs |
| `--scope`, `--forbid` (repeat) | allowed / forbidden path globs. `*` stays inside one path segment, `**` crosses segments, a glob without `/` also matches the basename. Take them from the task prompt |
| `--task-file` | checklist with `- [x]` / `- [ ]` items (counted, e.g. `tasks.md`) |
| `--pid-pattern` | regex matched against `ps` command lines. Make it specific (`codex exec.*stage-d`); `codex` alone also matches desktop helpers |
| `--state` | previous snapshot to compare with, then overwritten with this one |
| `--test-glob`, `--infra-glob` | extra globs for test files / test infrastructure, added to the built-in defaults (`*Tests.swift`, `*_test.go`, `*.test.ts`, `test_*.py`, `*Test.java`, `*_spec.rb`, `**/tests/**`, `**/__tests__/**` ...; mocks, fixtures, stubs, fakes, harness, testdata, snapshots) |
| `--error-pattern`, `--pass-pattern`, `--fail-pattern`, `--assert-pattern`, `--skip-pattern` | regex overrides for log and diff recognition |
| `--tail N`, `--recent N` | log lines analysed (300) and commits scanned for file churn (8) |
| `--config <file>` | `key=value` lines using the option names above (`scope=ios/**`, repeatable); default `<worktree>/.long-task-watch.conf` if present. CLI list options are appended |

Output is `key=value` lines; lists print `name_count=N` and `name[i]=...` (15 items max). Missing inputs print `n/a (...)`. Exit 2 means bad input (not a git worktree, unknown base, `--state` inside the worktree).

## Reading the facts

Default levels. The right-hand column is the first thing to check before believing a hit.

| Fact (key) | Normal | Watch | Needs a human | Usual false alarm |
|---|---|---|---|---|
| `forbid_hits_count` | 0 | | ≥ 1 | Glob too broad; generated file regenerated by the build |
| `out_of_scope_count` | 0 | 1–3 files | ≥ 4 files, or any source file unrelated to the task | Project files the build rewrites (lockfile, project manifest, localisation catalog); the task file itself |
| `logs_min_age_s` / `log[i].age_s` (agent still alive) | < 600 | 600–1200 | > 1200 **and** `delta_log_bytes=0` **and** `delta_tree_changed=no` | Long compile, simulator boot, or a test run that only prints at the end. Check `process[i]` cpu%: busy CPU means working |
| `process_alive=no` while the task is unfinished | | | yes, immediately | Agent finished normally: read its last message |
| `log[i].top_error_repeat_count` | ≤ 2 | 3–5 | ≥ 6, or ≥ 3 with the same sample two patrols in a row | Benign tool noise repeated by the toolchain (read the sample); a test log legitimately repeats names |
| `log[i].top_line_repeat_count` | < 10 | 10–25 | > 25 and not the same noise line | Hook or progress lines; many tests with similar names |
| `file_churn` (same file in ≥ 2 recent commits) | none | ≥ 3 of last 8 | ≥ 5 of last 8 for a file not meant to be central | Manifests and map/index files every phase must update (listed in `file_churn` always; ignore the expected ones) |
| `log_file_mentions` | < 5 | 5–14 | ≥ 15 for one file while `commits_since_base` does not move | The agent reading a file repeatedly is not editing it; weak signal |
| `commits_since_base` and `tasks_done` unchanged across 3 patrols | | 2 patrols | 3 patrols (≈ 1 h at 20 min) with live CPU or growing files | A single big task with a long test cycle; commit only at checkpoints |
| `test_to_source_ratio` | ≤ 1 | 1–2 | > 2, or `inf` with `test_added_lines` > 200 | Task is test-only (a test-writing phase); source added mostly in non-code files |
| `new_test_infra_count`, `new_test_dirs_count` | 0 | 1 | ≥ 2, or any not named in the plan | The plan explicitly asked for a fixture/seed file |
| `assert_lines_deleted` | 0 | | ≥ 1 | Deleted test for deleted code; check the commit message. A pure `assert_lines_modified` is Watch when the task changes expected behaviour, Needs-human when no spec change explains it |
| `skip_markers_added_count`, `commented_out_assertions_added_count` | 0 | | ≥ 1 | Skip added for a platform-only test that the plan allows |
| `uncommitted_files` large and `last_commit_age_s` large | commit every phase | 20+ files, 60+ min | 40+ files, 120+ min uncommitted | Agent commits only at a checkpoint, by design |

Interpretation notes:
- `delta_*` keys appear only with `--state`, and only for the second and later patrols. A first patrol has no trend; do not call it healthy on the absence of deltas.
- Assertion and skip detection looks at **test files only** and is regex-based: a custom assertion helper not in the pattern is invisible (pass `--assert-pattern`). `modified` counts removed assertion lines paired with added ones in the same hunk and usually means an expected value changed.
- `file_churn` counts commits since base only (at most `--recent`); `log_file_mentions` counts file basenames (≥ 8 chars) in the last `--tail` log lines. Both are best-effort and say nothing about uncommitted edits.
- Pass/fail markers are generic words (`passed`, `FAIL`, ...). A climbing `tail_fail_markers` with flat `total_pass_markers` over two patrols is a loop; a single high count is just a noisy log.

## Patrol

One-off: run the script, apply the table, report. Recurring: use a timer and keep `--state` constant so deltas appear.

- Interval 15–20 minutes. Shorter wastes tokens, longer lets a loop run an hour.
- Claude Code: schedule with `CronCreate` (`*/20 * * * *`) or `/loop 20m`; a cron or launchd job works for other setups.
- Prompt template for the timer:

```
Run ig-agent-watch for <worktree> (base <commit>, logs <paths>, scope <globs>, forbid <globs>,
task-file <path>, pid-pattern <regex>, state <path outside worktree>).
Apply the reading table. Report per the format; do not touch the agent or the worktree.
```

## Report format

All normal: one line, e.g. `[watch 14:20] ok: 3 commits (+1), tasks 20/29, tests 0.66:1, logs growing, process alive`.

Otherwise 2–3 lines: the level, the evidence (key and value, plus the log sample), and a suggested action for the human (inspect X, narrow the prompt, tell the agent to restore the assertion). Name each threshold you applied. Do not stop the agent; ask before any action that affects it.

## When the agent exits

Run one final patrol: `process_alive=no` is now expected, not a finding. Check the table's scope, forbid, assertion and skip rows against the final diff, then report to the human before accepting the work, and hand the diff to normal review. Stop the timer.

## Relation to other skills

- `ig-speckit-overrides` makes each checkpoint carry **Done when / Proven by** evidence; this skill is the in-flight check between checkpoints and does not replace that evidence.
- `spec-adversarial-review` critiques the proof architecture before the run; this skill watches behaviour during it. Run the review first when test bloat is a recurring problem.
